# Deadlock 1916 Sandbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a simple, animated WWI war-game map. Players set up a front on an editable ready-made map, press Go, nudge the battle with a few delayed orders, and see whether the deadlock breaks, how, and why.

**Architecture:**
- **Rules engine.** A new pure-TypeScript package, `packages/sandbox` (`@wwi/sandbox`), holds a small deterministic rules engine that steps a battle one minute at a time. All rule numbers live in one settings file.
- **Game page.** The UI is a new page in the existing app, `packages/app/sandbox.html` plus `src/sandbox/`. It runs the engine live on the main thread, so pausing and nudging act on live state.
- **Reuse.** It draws with the app's existing period-style helpers (`map/period.ts`, `map/style.ts`, `map/zoom.ts`).
- **Vimy app.** It stays as it is: same entry point, and its tests still pass.

**Tech stack:** TypeScript (strict), React 18, Canvas 2D, Vite (a multi-page build), Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-26-deadlock-sandbox-design.md` (approved 2026-11-26).

## Global Constraints

- **Browser-only static site.** It must work at 390 px phone width and from any sub-path (Vite `base: './'`).
- **Determinism.** The same setup plus the same seed gives an identical battle. Use one seeded RNG (mulberry32) passed explicitly. No `Math.random`, and no dependence on Map/Set iteration order.
- **Timing.**
  - A battle covers up to 2 days of game time.
  - At the default speed it plays in 2–5 minutes of real time.
  - One engine step (one game minute) takes no more than 2 ms on the default maps.
- **Rule numbers.** Every rule number lives in `packages/sandbox/src/settings.ts`. No magic numbers anywhere else.
- **Rules version.** `RULES_VERSION` (an integer, starting at 1) is bumped whenever a rule changes a battle's outcome.
- **Deadlock conditions,** as the owner ruled:
  - **breakthrough:** an attacking unit passes the defender's gun line before a defender reserve stands within `sealDistance` behind that line in its sector;
  - **surrender:** captured men ≥ 50% of the defender's men at Zero;
  - **collapse:** the defender's whole force, fit and still available, is below 10% of its men at Zero;
  - **stronghold:** the attacker holds every stronghold for 60 continuous minutes.
- **Zero** is the moment the player presses Go.
- **The Vimy app:** `npm test` and the existing e2e must still pass.
- **Commits:** end each commit with the session's `Co-Authored-By` and `Claude-Session` trailers.

## Review Focus

1. **An empty or one-sided setup** (no attackers, or no defenders) must not crash. The battle ends at once with "nothing to fight". *Task 4 test.*
2. **Units placed in a river or off the map** are refused at placement, with a short message; the battle never starts with them. *Task 6 test.*
3. **A share link made under an older `RULES_VERSION`, or a corrupt link,** loads with a plain notice, never a blank page. *Task 5 test.*
4. **A setup filled with the maximum `maxUnitsPerSide` on each side** still steps within 2 ms per minute. *Task 4 test.*
5. **Touch placement at 390 px.** Tapping places a unit and long-press removes it. *Task 6 e2e.*

### Task 2: Rules engine: units, fire, barrage, morale, movement

**Files:**
- Create:
  - `packages/sandbox/src/settings.ts`
  - `packages/sandbox/src/rng.ts`
  - `packages/sandbox/src/state.ts`
  - `packages/sandbox/src/step.ts`
- Test: `packages/sandbox/src/step.test.ts`

**Interfaces (produces):**
- `type Side = 'attacker' | 'defender'`
- `type Unit = { id; side; kind: 'battalion' | 'battery'; x; y; men; morale: number /* 0..1 */; suppression: number /* 0..1 */; status: 'waiting' | 'advancing' | 'holding' | 'pinned' | 'falling-back' | 'surrendered' | 'destroyed'; reserve: boolean; target?: { x; y } }`
- `type Line = { kind: 'trench' | 'wire'; side; points: [number, number][]; cut?: number }`
- `type Battle = { map: SandboxMap; settings: Settings; units: Unit[]; lines: Line[]; minute: number; rng: Rng; events: SandboxEvent[]; pending: Order[] }`
- `type SandboxEvent = { minute; kind: string; unitId?: string; why: string }`. `why` is one plain-language sentence.
- `step(b: Battle): Battle`, which advances one minute. It is pure: it returns a new `Battle`, built with structural sharing.
- `SETTINGS: Settings`, with these keys and defaults:

  | Key | Default |
  |---|---|
  | `mgLethality` | 0.004 |
  | `rifleLethality` | 0.001 |
  | `shellLethality` | 0.002 |
  | `barrageSpeedMPerMin` | 50 |
  | `barrageDepthM` | 150 |
  | `emergeMin` | 3 |
  | `advanceMPerMin` | 40 |
  | `wireSlow` | 0.25 |
  | `pinAt` | 0.6 |
  | `breakAt` | 0.25 |
  | `surrenderTrappedFrac` | 0.5 |
  | `orderDelayMin` | 20 |
  | `reserveMarchMPerMin` | 70 |
  | `sealDistanceM` | 1000 |
  | `strongholdHoldMin` | 60 |
  | `maxUnitsPerSide` | 40 |
  | `rangeM` | 800 |

  Each key has a one-line comment saying what it does.

**Rules** (keep them simple; this is the lesson set from Vimy):
- **Gap rule:** defenders in a trench under the attacker's barrage are suppressed. They man the parapet `emergeMin` minutes after the barrage lifts. An attacker within 50 m when the barrage lifts traps them, and `surrenderTrappedFrac` of the trapped men surrender.
- **Fire:** each unit fires at the nearest enemy unit in range (`rangeM`) and in line of sight. Line of sight is blocked by a higher cell or a wood between them. Losses are `men × lethality × (1 − cover)`, where cover comes from the target's terrain and whether it is in a trench. Fire raises suppression.
- **Morale:** losses and suppression lower morale. A unit is pinned below `pinAt` and falls back below `breakAt`. Morale recovers slowly when the unit is not under fire.
- **Movement:** advancing units move toward their target at `advanceMPerMin`, slowed by uncut wire, rising ground and wood. Shelling cuts wire.
- **Conservation:** `men + killed + wounded + captured` is constant for each unit.

**Steps:**
- [ ] **Step 1: Write the tests.**
  - A pinned unit doesn't advance.
  - The gap rule traps a garrison when an attacker is within 50 m at the lift, and does not trap it at 200 m.
  - Uncut wire slows an advance by at least half.
  - Line of sight is blocked by a ridge cell.
  - Conservation holds over 600 steps.
  - The same seed gives an identical `Battle` after 300 steps, and a different seed gives a different one.
- [ ] **Step 2: Run the tests and confirm they fail.**
- [ ] **Step 3: Implement.** Write `rng.ts` as mulberry32 with `next(): number` and `fork(label)`. The rest of the implementation is up to you.
- [ ] **Step 4: Run the tests and confirm they pass.**
- [ ] **Step 5: Commit.** Message: `feat(sandbox): rules engine`.

### Task 3: Orders and the computer opponent

**Files:**
- Create:
  - `packages/sandbox/src/orders.ts`
  - `packages/sandbox/src/ai.ts`
- Modify: `step.ts`, so that it applies due orders first and AI decisions second.
- Test: `packages/sandbox/src/orders.test.ts`

**Interfaces (produces):**
- `type Order = { side; kind: 'send-reserve' | 'barrage' | 'hold' | 'pull-back'; unitId?: string; at?: { x; y }; issuedAt: number; dueAt: number }`
- `issue(b: Battle, o: Omit<Order, 'issuedAt' | 'dueAt'>): Battle` sets `dueAt = minute + orderDelayMin`.
- `aiDecide(b: Battle, side: Side): Omit<Order, 'issuedAt' | 'dueAt'>[]`. This is the default behaviour:
  - **Defender:** sends its nearest reserve to a lost trench once it learns of the loss. It learns of a loss only when its own units can see it (picture-only, the Vimy lesson).
  - **Attacker:** advances behind its barrage line by line, and sends reserves to stalled sectors.
- `controller: Record<Side, 'human' | 'computer'>` goes on `Battle`. AI orders are issued only for sides the computer controls. Human orders are always allowed.

**Steps:**
- [ ] **Step 1: Write the tests.**
  - An order takes effect at `dueAt`, not before.
  - A `barrage` order shells the point for 10 minutes.
  - A `pull-back` order moves the unit away from the enemy.
  - The defender AI does not react to a loss its units cannot see.
  - With both sides on `computer`, a battle on each map runs to its end without error.
- [ ] **Step 2: Run the tests and confirm they fail.**
- [ ] **Step 3: Implement.**
- [ ] **Step 4: Run the tests and confirm they pass.**
- [ ] **Step 5: Commit.** Message: `feat(sandbox): delayed orders and computer opponent`.

### Task 4: Deadlock outcome, battle runner and balance check

**Files:**
- Create:
  - `packages/sandbox/src/deadlock.ts`
  - `packages/sandbox/src/run.ts`
  - `packages/sandbox/src/index.ts`
- Test:
  - `packages/sandbox/src/deadlock.test.ts`
  - `packages/sandbox/src/balance.test.ts`

**Interfaces (produces):**
- `type Outcome = { broken: boolean; by?: 'breakthrough' | 'surrender' | 'collapse' | 'stronghold'; minute?: number; margins: { beyondGunLineM: number; capturedFrac: number; fitFrac: number; longestHoldMin: number }; ended: 'deadlock-broken' | 'quiet' | 'time-up' | 'nothing-to-fight' }`
- `checkDeadlock(b: Battle): Outcome`. The gun line is the line through the defender batteries' positions, and it extends to the map edges.
- `startBattle(setup: Setup, seed: number): Battle`. `Setup` is from Task 5; declare its type here, in `types.ts`.
- `runToEnd(setup, seed, maxMin = 2880): { battle: Battle; outcome: Outcome }`
- The battle ends at the first of: deadlock broken, no fighting for 120 minutes, or `maxMin`.

**Steps:**
- [ ] **Step 1: Write the tests.**
  - Each of the four conditions is detected in a small staged battle.
  - An empty setup gives `ended: 'nothing-to-fight'` (Review Focus 1).
  - 40 units a side step in at most 2 ms per minute on average (Review Focus 4).
  - **Balance** (`balance.test.ts`): run computer against computer on each map with its default setup, over 20 seeds.
    - The deadlock breaks in 15–70% of runs on at least 3 of the 4 maps.
    - At least 2 different conditions occur across all runs.
    - If it fails, tune only `settings.ts`, then bump `RULES_VERSION`.
- [ ] **Step 2: Run the tests and confirm they fail.**
- [ ] **Step 3: Implement.** Also add default setups per map in `packages/sandbox/src/maps/<id>.setup.json`.
- [ ] **Step 4: Run the tests and confirm they pass.** Report the balance table in the commit body.

- `encodeSetup(s): string`: JSON, deflated with `CompressionStream`, then base64url-encoded. Provide a synchronous fallback, `encodeSetupSync`, for tests.
- `decodeSetup(str): { setup?: Setup; notice?: string }`:

- `validateSetup(s, map): string[]` returns the problems:
  - a unit in a river cell;
  - a unit off the map;
  - more than `maxUnitsPerSide` units on a side.

### Task 7: Play, nudge and result

  - `packages/app/src/sandbox/NudgeBar.tsx`
- Modify: `Sandbox.tsx`, which switches from setup to play on Go and has "Back to setup".
- Test:
  - `packages/app/src/sandbox/play.test.ts`
  - extend `e2e/sandbox.spec.ts`

**Behaviour:**
- **The play loop:** a `requestAnimationFrame` loop calls `step()` N times per frame, according to speed. There are four speeds: ½×, 1×, 4× and 16×; at 1×, a 2-day battle takes about 4 minutes. Pause and step-one-minute buttons are provided.
- **Drawing:** units are interpolated between minutes. Barrages are hatched, the front is shaded, and fire is shown as short tracer marks.
- **The nudge bar:** shown while the game is paused, or at any time on desktop. It offers Send reserve (pick a reserve, then a point), Barrage (pick a point), Hold, and Pull back (pick a unit).
  - Pending orders show a small clock with the minutes until they arrive.
  - Nudges are allowed for a human side only.
- **The event strip:** the last 5 events' `why` sentences.
- **The result card:** when the battle ends, a card shows:
  - "Deadlock broken by <condition> at <day hh:mm>" or "Deadlock held";
  - the closest margins;
  - buttons: "Replay same seed", "New seed", "Edit setup".

**Steps:**
